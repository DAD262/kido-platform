Mercado Pago en KIDO con identificación del comprador

Guía práctica para configurar, ejecutar y comprobar la integración ya construida en KIDO sin publicar el DNI real ni el Access Token.

Ambiente: pruebas · Moneda: PEN · Zona: Perú · Actualizado: noviembre de 2026

Resultado esperado. El estudiante crea la orden, acepta las condiciones comerciales, paga mediante Mercado Pago y KIDO confirma el pago consultando al proveedor. Solo después de validar importe, moneda, referencia, receptor y ambiente se habilita el curso.

1. Objetivo y alcance

Este manual documenta el código existente en kido-pago-ms, el frontend Angular y el Gateway. Sirve para una compra individual, carrito o certificado. Incluye Checkout Pro y el checkout interno; no inventa una aprobación: la respuesta visible del navegador nunca es suficiente para matricular.

Importante: “con mi DNI” no significa escribir tu DNI en el código. En KIDO, tu DNI real pertenece a tu perfil privado. En una compra de prueba se emplean únicamente datos de comprador de prueba autorizados por Mercado Pago.

5. Configuración segura

5.1 Credenciales de prueba

En el panel de Mercado Pago abre tu aplicación, entra a Credenciales de prueba y copia las credenciales correspondientes. La clave pública puede estar en el frontend para inicializar el SDK; el Access Token es privado y solo lo usa el backend.

Archivo local raíz .env (no debe subirse a GitHub):

MERCADO_PAGO_ACCESS_TOKEN=<ACCESS_TOKEN_DE_PRUEBA>
MERCADO_PAGO_PUBLIC_KEY=<PUBLIC_KEY_DE_PRUEBA>
MERCADO_PAGO_AMBIENTE=pruebas
MERCADO_PAGO_RETURN_URL=http://localhost:4300/pago/resultado
MERCADO_PAGO_AUTO_RETURN=false
MERCADO_PAGO_NOTIFICATION_URL=
MERCADO_PAGO_WEBHOOK_SECRET=
MERCADO_PAGO_MODELO_RECAUDACION_CONFIRMADO=false

Las propiedades se consumen desde infra/kido-config/config-repo/kido-pago-ms-dev.yml. El repositorio solo conserva nombres de variables y valores no sensibles.

No copies el prefijo de un ejemplo. Pega exactamente la credencial de prueba que entrega tu aplicación de Mercado Pago; KIDO además consulta /users/me para verificar que la cuenta sea de Perú y del ambiente configurado.

7. Compra de prueba, paso a paso

1
Inicia sesión como estudiante y abre un curso de pago no comprado.
2
Pulsa comprar, revisa el precio, selecciona Mercado Pago y acepta el aviso de entorno de prueba.
3
En el checkout usa únicamente una cuenta compradora y un medio de prueba. No uses la misma cuenta vendedora para comprar.
4
Para simular aprobación utiliza el nombre de titular de prueba APRO y el documento de prueba que muestre la documentación vigente de Mercado Pago para Perú. Al momento de redactar esta guía, la página oficial indica 123456789.
5
Al volver a /pago/resultado, KIDO consulta la orden. El curso debe aparecer en “Mis cursos” solamente cuando el backend confirme approved.
Los datos de prueba pueden cambiar. Antes de probar, consulta la tabla oficial enlazada al final. No conviertas números de prueba en constantes del proyecto.

8. Líneas de código explicadas

8.1 Preferencia de Checkout Pro

req.put("items", items);                 // cursos y precios calculados por KIDO
req.put("external_reference", referencia); // une el pago con la orden interna
req.put("statement_descriptor", "KIDO");  // texto comercial
req.put("notification_url", notificationUrl); // webhook HTTPS
POST /checkout/preferences              // se ejecuta solo en el backend

8.2 DNI en el checkout interno

payer: {
  email,
  first_name: nombres,
  last_name: apellidos,
  identification: { type: "DNI", number: documento }
}

KIDO incorpora identification cuando el medio seleccionado lo requiere, como pagoefectivo_atm. El backend acepta DNI, CE, RUC o PAS y valida entre 6 y 20 caracteres alfanuméricos. Para tarjeta, los datos sensibles los tokeniza el SDK de Mercado Pago; KIDO no debe almacenar el número ni el CVV.

8.3 Confirmación segura

POST /api/v1/pagos/ordenes/{id}/confirmar-mercado-pago?paymentId={paymentId}
GET  https://api.mercadopago.com/v1/payments/{paymentId}

El primer endpoint pertenece a KIDO. Después, el backend consulta al proveedor con su Access Token y no confía en parámetros editables del navegador.

9. Webhook en desarrollo

localhost no es accesible desde Mercado Pago. Publica temporalmente el Gateway con HTTPS (por ejemplo, mediante un túnel autorizado) y configura:

MERCADO_PAGO_NOTIFICATION_URL=https://TU-DOMINIO/api/v1/pagos/webhooks/mercado-pago
MERCADO_PAGO_WEBHOOK_SECRET=<FIRMA_SECRETA_DEL_PANEL>

En el panel de Webhooks selecciona el evento de pagos. KIDO valida x-signature y procesa de forma idempotente: repetir la misma notificación no debe duplicar la inscripción. El endpoint responde rápido y la lógica consulta el pago real por su identificador.

10. Cómo comprobar que sí funciona

  1. /api/v1/pagos/metodos muestra Mercado Pago disponible y ambiente pruebas.
  2. Al comprar se crea una orden con PAGO_INICIADO y una referencia externa.
  3. El enlace de checkout pertenece a un dominio oficial de Mercado Pago.
  4. Tras aprobar, la orden queda APROBADA, guarda el paymentId y la inscripción queda sincronizada.
  5. Actualizar la página no crea una segunda inscripción.
  6. Un monto, moneda, receptor o referencia diferentes son rechazados.

Pruebas automatizadas

cd services\kido-pago-ms
.\mvnw.cmd test

Las suites cubren creación de preferencia, importes, moneda, identidad del receptor, firma del webhook e idempotencia. Una prueba automatizada aprobada confirma la lógica local; la prueba end-to-end con cuenta de prueba confirma además credenciales, red y configuración externa.

SíntomaCausa probableCorrección
“Mercado Pago aún no está habilitado”Access Token vacíoCompleta el .env local y reinicia Config Server/pago-ms.
“Cuenta no corresponde al ambiente”Credencial productiva con pruebas o viceversaUsa credenciales y ambiente de la misma aplicación.
No aparece el retornoURL local no aceptada para auto-returnMantén AUTO_RETURN=false en local o usa HTTPS público.
PagoEfectivo dice documento inválidoTipo/formato incorrectoSelecciona DNI y escribe solo los dígitos permitidos; en pruebas usa datos de prueba.
El pago aprobó pero no hay cursoServicio de inscripción caído o webhook sin accesoRevisa Eureka, logs de pago/inscripción y ejecuta la verificación de la orden.
401 en GatewaySesión o JWT ausente/vencidoVuelve a iniciar sesión; el webhook es la única ruta de pago pública.

12. Paso a producción

No cambies solo el token. Producción requiere HTTPS, credenciales productivas, webhook firmado, URLs públicas, información comercial publicada y confirmación del modelo de recaudación/liquidación.
  • MERCADO_PAGO_AMBIENTE=produccion.
  • Access Token productivo guardado como secreto del servidor.
  • RETURN_URL y NOTIFICATION_URL con HTTPS.
  • Firma secreta del webhook configurada.
  • MERCADO_PAGO_MODELO_RECAUDACION_CONFIRMADO=true solo después de la confirmación correspondiente.
  • Compra real controlada de importe mínimo, conciliación, reembolso y monitoreo.
